# libvisualmemory backlog (known, deliberately deferred)

Status as of Stage 2 finalisation. IDs are stable; reference them in commits/issues.

| ID | Item | Why it matters / evidence | Proposed work |
|---|---|---|---|
| VM-1 | **FAT32 directory limit / hourly partitioning** (Stage 1) | The real store on the XT5 SD card (FAT32) held 17,539 JPEGs in one day directory in earlier testing; FAT32 directory lookups/creates slow down and have hard entry limits. | Partition `frames/YYYY/MM/DD/HH/<source>/`; keep the relative-path column so old rows stay valid; test migration + retention across the new layout. |
| VM-2 | **Write-failure logging / health** | Stage 1/2 count `write_fail`, `db_fail`, `perm_fail` etc. but there is no dedicated rate-limited log line or exposed health flag when storage is failing (ENOSPC, EIO, SD removed). | Rate-limited WARN with errno + path; export failure counters via the existing metrics endpoint; add a degraded flag. |
| VM-3 | **sqlite-vec v0.1.6 leak** | `vec0_free()` does not free the metadata-chunk-name strings: 2 small allocations per vec0 table per connection (ASan). One-off per connection, not per query. | Track upstream; re-check on upgrade; if upgrading is not possible patch via a documented local patch file (vendored source is currently unmodified). |
| VM-4 | **Search scaling** | vec0 is an exact scan, ≈4 µs/vector on the XT5 (10k: 41 ms p50, 68 ms with a time window - metadata filters do not reduce the scan). 7 days at 5 s cadence is ≈120k vectors/source ≈ 0.5 s per query while holding the DB mutex. | Time-partitioned vec0 tables (drop whole partitions for retention and search only relevant ones), bound queries by default time range, or an ANN index above ~100k vectors; move queries to a read-only connection. |
| VM-5 | **Preprocessing optimisation** | pp1 resize is scalar C++: ≈10.9 ms idle, p95 ≈52 ms under detector load - larger than the 5.9 ms inference. Not a problem at 5 s cadence. | NEON separable resize or RGA/libyuv-assisted downscale, validated against `reference_embedder.py` (numerics must not change pp1). |
| VM-6 | INT8 retrieval quality | top-5 overlap 0.86 vs ONNX on device; 41-image calibration set. INT8 is **not enabled**. | Only revisit with a representative calibration set and a retrieval-based acceptance test. |
| VM-7 | Model licensing / distribution | ImageNet-trained weights; commercial terms unresolved; binaries kept out of git. | Legal sign-off or replace the model (new `model_version`); publish binaries to the artifact store (see `models/README.md`). |
| VM-8 | SD commit-latency tail | vec insert p99 ≈ 0.95 s, max ≈ 1.2 s on SD (worker thread only; capture is not blocked; Stage 1 DB writes show the same tail). | Group commits / WAL experiments on the target card; keep off the capture path. |
| VM-9 | Dashboard API access control | The dashboard (port 20300/…) is open on the LAN like the existing audience dashboard; `dashboard.vm_token` is optional and off by default. Frames contain camera images of people. | Decide a deployment default (token on, or LAN-only firewalling); TLS is not provided. |
| VM-10 | ~~Dashboard runtime snapshot not yet exercised on the XT5~~ | Closed: exercised on the XT5 (live counters in the dashboard, 5 s cadence, atomic writes). | — |
| VM-12 | USB camera drops to ~19 fps in dim light | Cause (measured with Argus stopped): UVC `exposure_auto_priority=1` lets the camera lower its frame rate; the camera comes back with 1 after every power-up. Fixed per deployment with the optional `input.usb.exposure_auto_priority` setting (0). Trade-off: darker/noisier image in dim light (not yet measured in a dim room). | Measure image quality at low light with 0; decide the product default. |
| VM-13 | File input is not real-time paced and `input.file.loop` is not read from the JSON config | Observed while preparing the demo dataset: a video decodes as fast as possible (`sync=false`) and ends immediately ("no loop"), so a slideshow video cannot be replayed through the capture pipeline at 5 s per scene. The demo dataset is therefore ingested with `vm_ingest_dir` (real writer + NPU embedder). | Out of scope for Visual Memory; file input untouched. |
| VM-11 | Search is exact and single-flight | One search at a time (429 otherwise); a 10 s deadline interrupts SQLite; scales per VM-4. | Revisit with time-partitioned tables. |
| VM-14 | D4 object index: exact scan, no dashboard delete | `objects.db` BLOB vectors are scanned exactly (62 ms at 10,000 regions on the XT5, linear). Regions can only be deleted through the library (`delete_region`), not the dashboard. A region query is ~3× slower than an ROI query at 100/1,000 regions (cause not identified). | ANN/sqlite-vec for the object table beyond ~50k regions; add a delete/relabel endpoint; investigate the `region_id<>?` plan. |
| VM-15 | FAT32 daily-directory overflow (RESOLVED in D5 for new data) | `frames/YYYY/MM/DD/` holds every frame of a day (FAT32 ≈ 65k entries/dir; 5 s cadence is 17k/day, but D5 screenshots and shorter intervals can exceed it). D4 writes no per-object files. | Hourly partitioning `frames/YYYY/MM/DD/HH/<source>/` with backward-compatible relative paths in `frames.relative_jpeg_path`; required before sustained automatic capture (D5). |
| VM-21 | ~~Startup retention stalled ingestion~~ (RESOLVED) | The writer ran retention to completion before it started draining its queue. A store with an old expired backlog (XT5: ~14,000 frames) dropped every sample as "queue full" for ~11 min and stored nothing; the periodic pass stalled the writer ~0.5-1 s every minute. Found on the XT5 on 2026-11-05 (newest stored frame 2 days old while Argus ran at 29 FPS). | Retention now runs in short budgeted slices (default 100 ms / 64 deletions) between frames, with a guaranteed-progress rule; `Stats` gained `last_commit_utc_ms`, `retention_pending`, `retention_slice` and `commit_delay` latency. Startup backfill is capped (`backfill_max_frames` 500, `backfill_max_age_hours` 24). Regression tests: `VisualMemory.ExpiredBacklogDoesNotStallIngest`, `Retention.Budgeted*`, `tests/browser/vm_gallery_live_cdp.py`. |
| VM-16 | D5: no wall clock in BrightScript on this firmware | `roDateTime` is epoch 0 and `roSystemTime` cannot be created on BrightSignOS 9.1.139, so the player application reports `mono_ms` only and the adapter assigns UTC when it reads the event (error about one poll period, 200 ms, plus the player's flush delay). Events read long after they were written (adapter down) are stamped late. | Report an NTP-synchronised epoch from the player application when the firmware allows it. |
| VM-17 | D5: `Screenshot()` returns before the file is complete | Seen on the XT5: a successful call, then "Premature end of JPEG file". The adapter waits for the EOI marker and a stable size (up to 4 s) and records a failed capture otherwise. | Ask BrightSign whether `Screenshot()` has a synchronous mode. |
| VM-18 | D5: live-stream verification needs same-time references | A live source (RTSP) changes, so references sampled earlier do not match (sim 0.77 vs 0.80 threshold). The validated procedure samples supplemental source frames during the play (`make_reference_frames.sh` + `references/build?replace=1`); those frames are supplemental, not HDMI proof. | A source-side frame tap in the player application. |
| VM-19 | D5: only file and RTSP playback validated | HTML5 `<video>`, HLS/UDP, multi-zone layouts, DRM content and HDMI-input playback are not tested; display capture of those paths is unverified. | Extend the validation matrix before claiming support. |
| VM-20 | D5: thresholds calibrated on two advertisements | `match_sim 0.80` separated matches (0.90-0.99) from wrong content (0.57-0.59) here; similar-looking ads or short scenes may need per-asset thresholds and more reference frames. | Per-asset calibration and a confusion test with look-alike ads. |
